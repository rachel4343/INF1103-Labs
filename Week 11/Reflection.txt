8.	Reflection task (Optional) 
•	Where in your system, would adding a pattern, make the design more complicated than it needs to be? 
Adding a design pattern is not always necessary because it can introduce extra classes and relationships that make the system harder to understand. For example, creating a separate strategy class for every small operation in the Inventory system would be unnecessary if the operations are simple and unlikely to change. A design pattern should only be introduced when it solves an actual design problem, such as reducing duplicated code, improving flexibility or making future changes easier. Therefore, I should choose patterns based on the needs of the system rather than using them simply because they are available.

•	The Factory moved the OCP issue from the client into the factory. Is that a good trade-off for your system? Why? 
Yes, I think it is a good trade-off for my Inventory Management System. Before introducing the Factory Pattern, main.py and inventory.py needed to know how to create different product types, which meant adding a new product type could require changes in multiple places. With ProductFactory, object creation is centralised in one location. If object creation code needs to change, we only need to change it in one place within ProductFactory class itself. Although the factory itself still needs to be updated when a new product type is introduced, the other parts of the system can continue requesting products through the same create() method. This reduces changes across the system and makes product creation easier to maintain.

•	In 5.2, you skipped bad rows and kept loading. When would rejecting the whole file be the better design decision? 
Rejecting the entire file would be better when the data must be complete and consistent for the system to function correctly. For example, if a CSV file contains financial transactions, payment records or important inventory updates that must all be processed together, loading only some records could produce inaccurate results. In such situations, accepting valid rows while skipping invalid ones could leave the system with incomplete or inconsistent data. Rejecting the entire file would prevent partial updates and allow the user to correct the errors before attempting to load it again. For my current inventory example, skipping invalid rows is acceptable because the valid products can still be added independently.


•	What is the difference between a validation failure and an exception in your code? Give one example of each. 
A validation failure occurs when the program successfully receives and processes a value but discovers that it does not follow the required rules. For example, when a user enters -5 as a product price, Python successfully converts it into a float, but the validation condition value <= 0 identifies it as invalid. The program displays an error message and asks the user to try again. An exception occurs when an operation cannot be completed normally. For example, entering abc as a product price causes float("abc") to raise a ValueError because the text cannot be converted into a number. The except ValueError block catches the exception and allows the program to continue instead of crashing.

One possible difference I encountered was during the CSV loading test. Initially, I expected the load_products() function to automatically load the products when I ran main.py. •	Where in your group project could the Strategy or Factory pattern help, or would it be over-engineering? Why?
In our PhishGuard group project, the Strategy Pattern could be useful for handling different threat assessment or risk-scoring approaches. For example, we could have separate strategies for different ways of calculating phishing risk while allowing the main logic to use a common interface. This would make it easier to introduce or change scoring methods without modifying the main report-processing logic. The Factory Pattern could also be useful if the system needs to create different types of security reports or review objects based on their categories. However, introducing these patterns would be unnecessary if the current implementation only has a small number of straightforward creation or scoring rules. Therefore, I would only introduce them when the project becomes more complex and the patterns provide a clear improvement in maintainability and flexibility.
